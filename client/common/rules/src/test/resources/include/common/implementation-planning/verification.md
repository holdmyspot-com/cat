# Implementation Planning Acceptance

These fixtures assess planning decisions through the installed plugin and native harness. They are focused behavioral
checks, not statistical certification or evidence of an elapsed-time improvement. Each JSONL file is an independent
runner request containing an ordinary task and a completion message. Copy only the empty `project` fixture into the
isolated run; keep this document and its assertions outside the executor's inputs.

## Design Checkpoint

The required reader result is a plan that covers the requested outcomes, questions unsupported design premises, and
selects coherent assignments, dependencies, detail, ownership, and checks from the available evidence. The minimum case
is an importer whose deduplication design assumes an identity property that has not been established. A file-format
migration reaches the same decision through a different mechanism: its assumed atomic publication must be established
before dependent recovery behavior is fixed. The identity premise affects durable deduplication and restart decisions;
the publication premise affects reader visibility and recovery. Both require an early evidence task before those
dependent branches expand, with conditional dependent decisions while independent work proceeds. A plan that merely
promises to repair those branches after a late check does not satisfy this proactive outcome.

The same prevention applies outside implementation planning: an unresolved population criterion can change results
across an analysis batch. Settle that shared criterion before producing dependent results. This comparison places the
invariant in Monotonic Progress, whose workflow scope includes both cases, while Design Quality retains its specific
design-validity and integration checks. No new record format or execution mechanism is part of this invariant.

A stable batch of independent exporters is the nearest counterexample: its shared contract has broad downstream use
but is already established. It permits detailed upfront assignments and concurrent work without a repeated premise
probe. A small cohesive fix needs one owner and a short sequence. A spelling correction in text that mentions an
implementation plan does not ask for a planning decision.

The surviving invariant is full outcome and dependency coverage with implementation detail and execution boundaries
chosen from actual uncertainty, coupling, and verification needs. The implementation-planning rule owns those choices.
Design Quality continues to own design validity and handoff compatibility; Delegation owns assignment and integration
mechanics. Monotonic Progress owns early premise checks that limit avoidable invalidation, and preservation or explicit
invalidation of accepted work when evidence changes. The plan-builder and plan-review bodies own their role-specific
outputs and route to the shared rule.

The new rule's first goal is checked by outcome coverage and assignment readiness; its second by the different choices
for uncertain, stable, and small work; its third by a second importer turn that supplies new identity evidence and a
completed independent result. These are distinct decisions with a prerequisite relationship: evidence establishes
which later assignment can be completed and released. The added Monotonic Progress goal acts before dependent work
begins; its retained transition goal governs later reuse or invalidation, and its concurrency goal governs independent
execution. Early premise checks do not require a new progress record when no workflow progress is being recorded for
later use. Existing role constraints remain unchanged. The default route is conditional on a planning decision and
excludes the mechanical text edit.

### Coverage Representations and Conditional Test-First Work

The additional reader result is a plan that selects enough representation to cover the required behavior, then assigns
coherent verifiable work independently of that representation's size. The minimum concrete case is an article passing
between an author and reviewer across saved drafts, return visits, requested changes, and publication. Separate screen
descriptions can omit those transitions. Journey coverage exposes the omissions; use cases or equivalent contracts
establish outcomes and relevant alternatives; assignments deliver bounded portions with acceptance evidence.

The analogous shared-filter case has two machine callers and an established identity contract. It needs behavior and
consumer coverage, but one shared-capability assignment can preserve consistency without a user-journey document. The
dissimilar local formatter case already has the needed regression and no experience transitions to discover. The
surviving invariant is coverage and coherent verifiability, not a mandatory document or a universal work-unit shape.
Implementation Planning owns this representation and assignment decision; Design Quality retains design validation.
Its additional coverage goal complements assignment readiness: coverage identifies what must be delivered, while
readiness determines whether a selected portion can be handed off.

For test-first work, the concrete shared-filter case has a settled contract and a runnable missing-behavior check, so
its plan must preserve the behavioral red gate. The analogous local cache correction remains eligible even while an
independent provider-identity premise is unresolved. The attempted cache test's compilation failure establishes no
behavioral red result. The dissimilar provider mock merely encodes the unverified replay guarantee; making it fail and
pass cannot establish that guarantee. The surviving invariant is an established expected outcome and evidence at the
claimed boundary. TDD owns the red gate and the narrow enabling-implementation exception; Monotonic Progress owns
authentic premise checks and independent progress. The TDD applicability addition establishes the expected contract
before its existing red-gate obligations can apply. It does not weaken those obligations for ready testable behavior.

### Planning-Route Application

The journey and shared-capability runs received the existing planning trigger in SessionStart context but returned
plans without reading its target. The shared-capability run also tried nonexistent skills. Source, packaged, and
installed rule hashes matched; the observed failure was application of the delivered route. The traces establish the
skipped read and substituted paths, but do not establish a private reason for either decision.

The earliest controllable decision is completing the task-triggered rule read before inspecting the project or deriving
the plan. The journey case needs that step for experience coverage; the shared internal component needs the same step
for behavioral assignments; the small cohesive fix still needs it without extra documents or owners. The mechanical
text correction does not make a planning decision and must remain outside the route. Conditional TDD is a retained
positive case: its supported premise and red-gate distinctions must survive the routing correction.

Default Rule Routing owns the decision while the planning body is not yet available. Its existing specialized-routing
goal covers this action, and its root-derivation goal is a prerequisite for the displayed read. The distinct
input-preservation goal is unaffected. Replace the existing planning route in place with the executable read and its
decision boundary; retain one route and reuse the existing root-derivation and literal-target procedure. Planning and
TDD retain their downstream decisions. Moving the route has no established causal basis, and unconditional delivery
would change its audience rather than establish selective routing.

Hold the original tasks, fixture, model, reasoning setting, and other guidance fixed when comparing this route wording.
Record reads and semantic decisions separately. For this focused regression, repeat each reported case against the
control once, then require two fresh candidate trials of each reported case plus the small-cohesive, mechanical-text,
and conditional-TDD cases to satisfy their assertions. This finite check supplies regression evidence, not a reliability
percentage. Retain any failed condition through later revisions.

One journey run successfully read TDD's complete-project verification requirement, then returned focused and connected

Implementation Planning owns this translation under its outcome-coverage and verification-scheduling goals. TDD remains
the single owner of which verification it requires before handoff; Default Rule Routing remains unchanged.

The correction replaces the generic instruction to preserve terminal gates with an explicit derivation and scheduling
step after loading the applicable verification rules. Compare two fresh journey trials, then retain the shared-capability,
small-cohesive, conditional-TDD and mechanical-text decisions in one fresh trial each. Require both guidance delivery and

The first correction merged the testing and TDD routes into one paragraph. Both journey trials named the project gate
but skipped the TDD read, reopening an already satisfied routing condition. Retain that failed candidate as evidence;

Separating and clarifying that route still left both journey trials without a TDD read, despite receipt of the complete

With the route at entry, both journey trials read TDD and scheduled the project gate, but the shared-capability trial

That executable reference alone still left both journey trials without TDD. Their traces show the foundational-rule

## Assertions

For the eight ordinary-agent cases, inspect retained native events separately from the terminal response. For planning
cases, require a successful read of the evaluated artifact's `rules/include/common/implementation-planning.md` before
the first project inspection or decision about behavior coverage, assignments, dependencies, or checks, then evaluate
the decisions below. An unsuccessful lookup or a substituted skill does not satisfy that read; a later read cannot
retroactively accept an earlier governed decision. The task does not name that rule. For named agents, also require
evidence that the runner delivered the selected agent's assembled developer contract. An installed file's existence or
a build result does not establish either delivery or application.

For the first `uncertain-boundary` turn, require a successful read of
`rules/include/common/monotonic-progress.md` before the initial plan, while the premise is unresolved and no importer
work has been accepted. The plan must name concrete downstream decisions that depend on activity identity and assign
the authentic identity check before making those implementation assignments unconditional. The read-only planner
must not execute the probe or count the scheduled check as evidence that the premise is established. Reject a plan
that permits dependent implementation to finish before its first identity check, even if it promises later repair.

In the second turn, the already loaded rule remains available; do not demand another read. The reader must reuse the
new authoritative `activity_uid` evidence without an unnecessary repeat probe, retain the verified admin-status result
under its unchanged status API, make the identity-dependent importer assignments ready, and keep restart and
service-boundary acceptance open. Reject a full reset of the plan or a stale `event_id` assignment. The stable and small
cases must remain eligible without an invented premise probe. Loading the proactive guidance alone must not cause a
new progress ledger; any progress-record requirement must follow the retained workflow-recording condition.

For `journey-coverage`, `shared-capability` and `conditional-tdd`, require a successful read of the evaluated artifact's
`rules/include/common/tdd.md` before the plan fixes production-edit order. In `conditional-tdd`, also require a successful
read of `rules/include/common/monotonic-progress.md` while the provider premise remains unresolved. A read-only planner
schedules the required checks; it must not claim that the fixture's compilation failure or a planned test is an observed
behavioral red result. Assess TDD selection separately from correct application.

In these three cases, require the plan to schedule TDD's complete-project verification after the relevant focused and
integration checks and before implementation handoff. A complete user journey establishes only that experience; it does
not establish the project's complete verification gate. Naming the governing rule without scheduling its required
check is insufficient. The planner must not claim that these future checks have already run or invent a project command
that the supplied scenario does not establish.

The changed behavior requires semantic assessment of the resulting plan. Literal phrase checks would not distinguish a
valid alternative plan from an incorrect one, so these live traces and case assertions are the focused acceptance
boundary. No automated behavioral red-test result is claimed.

Across planning responses, reject unsupported numerical durations, universal speed claims, or scope substitutions.
Accept different decompositions when their stated dependencies and checks satisfy the case. Do not grade by literal
phrases from the rule. If a trace cannot establish guidance selection or delivery, leave that claim unverified even
when the plan itself is good.

## Commands

Run from the repository root. Build the current artifact before using it:

```bash
client/mvnw -q -Dmaven.build.cache.enabled=false -f client/pom.xml verify
```

Run the ordinary Codex cases:

```bash
planning_tests=client/common/rules/src/test/resources/include/common/implementation-planning
for planning_case in uncertain-boundary cross-mechanism stable-batch small-cohesive journey-coverage shared-capability conditional-tdd mechanical-text; do
  client/common/distribution/target/jlink/codex/bin/codex-runner \
    --artifact client/common/distribution/target/runtime/codex \
    --project "$planning_tests/project" \
    --install-cat --exclude-user-rules --keep-run \
    < "$planning_tests/$planning_case.jsonl" || exit $?
done
```

Run the named agents in both harnesses:

```bash
planning_tests=client/common/rules/src/test/resources/include/common/implementation-planning
for planning_harness in codex claude; do
  "client/common/distribution/target/jlink/$planning_harness/bin/$planning_harness-runner" \
    --artifact "client/common/distribution/target/runtime/$planning_harness" \
    --project "$planning_tests/project" \
    --agent plan-builder-high \
    --install-cat --exclude-user-rules --keep-run \
    < "$planning_tests/uncertain-boundary.jsonl" || exit $?
  "client/common/distribution/target/jlink/$planning_harness/bin/$planning_harness-runner" \
    --artifact "client/common/distribution/target/runtime/$planning_harness" \
    --project "$planning_tests/project" \
    --agent plan-review-high \
    --install-cat --exclude-user-rules --keep-run \
    < "$planning_tests/review-incomplete-plan.jsonl" || exit $?
done
```

Retain each returned run identity, terminal status, native trace, and assertion assessment for the parent accepting the
change. The parent owns final evidence retention and cleanup. A runner failure is evidence only for the boundary that
failed; do not count an unexecuted case as a behavioral failure or success. Report build, routing, application, named-agent
delivery, and scope-preservation gates separately. Keep any failed or unrun required gate open.
