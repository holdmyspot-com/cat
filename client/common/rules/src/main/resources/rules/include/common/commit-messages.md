# Commit Messages

## Design Goals

- Let a reader of the history learn why each commit was made, not only what it changed, without asking its author or
	finding a discussion that the history does not record.

## Guidance

When creating or revising a Git commit message, state why the change was made as well as what it changes: the problem,
defect, need, or goal that required it, in terms a reader of the history can understand without the conversation that
produced it. Put the reason in the summary when it fits concisely; otherwise add a body that states it. A restatement of
the change, a list of edited files, an implementation step, or "as requested" is not a reason. When a request prompted
the change, state what the request needed and why. Follow the project's own format for the summary line when it
defines one.
